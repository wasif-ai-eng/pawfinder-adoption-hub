1. Executive Summary

PawFinder is a full-stack database application designed to streamline community pet adoption and foster workflows. The primary objective of this project is to apply theoretical relational database concepts—specifically Boyce-Codd Normal Form (BCNF), declarative integrity constraints (CHECK, UNIQUE, NOT NULL), referential integrity actions (ON DELETE CASCADE), and relational database views—to a real-world multi-user application.

2. Entity-Relationship (ER) Modeling

The system is modeled around four core entities that capture the operational lifecycle of a pet adoption exchange:

  • USERS: Represents both pet owners and prospective adopters.
  • SPECIES: Standardized taxonomy classifying pet types (Dog, Cat, Bird, Rabbit).
  • PETS: The focal resource containing age, breed, description, and status.
  • ADOPTION_REQUESTS: Transactional records capturing adoption applications, requested handover dates, and home details.

3. Relational Schema & Normalization Analysis

3.1 Normalization Derivation

A common anti-pattern in naive adoption platforms is storing freeform species names directly within the pets relation. Consider the unnormalized dependency: 

pet_id -> name, breed, species_name, owner_id

This structure exhibits both update and deletion anomalies. If all dogs in the database are adopted and deleted, the classification "Dog" would be inadvertently purged from the system.

Decomposition to BCNF: The schema was decomposed into pets and species. The functional dependencies for each table are:

  • species_id -> species_name (Where species_id is candidate key)
  • user_id -> full_name, email, city, created_at (Where user_id is candidate key)
  • pet_id -> owner_id, species_id, name, breed, age_months, status (Where pet_id is candidate key)
  • request_id -> pet_id, adopter_id, status, preferred_date, home_description (Where request_id is candidate key)

Since for every non-trivial functional dependency \( X \rightarrow Y \), \( X \) is a superkey, the entire database satisfies Boyce-Codd Normal Form (BCNF).

4. Data Definition Language (DDL) Implementation

The following SQL DDL defines the relational tables and integrity constraints:

-- 1. USERS
CREATE TABLE IF NOT EXISTS users (
    user_id SERIAL PRIMARY KEY,
    full_name VARCHAR(100) NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL,
    city VARCHAR(50) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- 2. SPECIES
CREATE TABLE IF NOT EXISTS species (
    species_id SERIAL PRIMARY KEY,
    species_name VARCHAR(50) NOT NULL UNIQUE
);

-- 3. PETS
CREATE TABLE IF NOT EXISTS pets (
    pet_id SERIAL PRIMARY KEY,
    owner_id INT NOT NULL,
    name VARCHAR(150) NOT NULL,
    species_id INT NOT NULL,
    breed VARCHAR(80),
    age_months INT CHECK (age_months >= 0),
    description TEXT,
    status VARCHAR(20) DEFAULT 'Available' 
        CHECK (status IN ('Available', 'Adopted', 'Pending')),
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_owner FOREIGN KEY (owner_id) REFERENCES users(user_id) ON DELETE CASCADE,
    CONSTRAINT fk_species FOREIGN KEY (species_id) REFERENCES species(species_id) ON DELETE CASCADE
);

-- 4. ADOPTION REQUESTS
CREATE TABLE IF NOT EXISTS adoption_requests (
    request_id SERIAL PRIMARY KEY,
    pet_id INT NOT NULL,
    adopter_id INT NOT NULL,
    status VARCHAR(20) DEFAULT 'Pending' 
        CHECK (status IN ('Pending', 'Approved', 'Rejected', 'Completed')),
    requested_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    completed_at TIMESTAMP WITH TIME ZONE NULL,
    preferred_date DATE NULL,
    home_description TEXT NULL,
    CONSTRAINT fk_pet FOREIGN KEY (pet_id) REFERENCES pets(pet_id) ON DELETE CASCADE,
    CONSTRAINT fk_adopter FOREIGN KEY (adopter_id) REFERENCES users(user_id) ON DELETE CASCADE
);

5. Relational SQL Views

A database view was created to simplify reporting and eliminate join duplication in client components: 

CREATE OR REPLACE VIEW available_pets AS
SELECT 
    p.pet_id,
    p.name,
    s.species_name,
    p.breed,
    p.age_months,
    p.status,
    u.full_name AS owner_name,
    u.email AS owner_email
FROM pets p
JOIN species s ON p.species_id = s.species_id
JOIN users u ON p.owner_id = u.user_id;

7. Conclusion

The PawFinder project provides an end-to-end realization of database management system principles. By strictly enforcing domain constraints, referential integrity with cascading deletions, and 3NF/BCNF normalization, the system provides guaranteed data integrity and zero redundancy across the pet adoption lifecycle.
