System Context

Problem Statement & Motivation

  • Disorganized Adoption Pipelines: Adoptions managed over social media or messaging lack structured relational tracking.
  • Referential Integrity Failures: When listings are deleted or users leave, existing inquiries become orphaned without DBMS constraints.
  • Data Redundancy: Repeatedly storing freeform species names leads to update and deletion anomalies.
  • The PawFinder Objective: Design a strictly normalized relational database system that models pet listings, species categories, and adoption transactions with database-level integrity enforcement.

Logical Schema

Relational Schema & Constraints

Table Primary Key Foreign Keys Key Constraints
users user_id None email UNIQUE NOT NULL
species species_id None species_name UNIQUE NOT NULL
pets pet_id owner_id, species_id status IN ('Available','Adopted','Pending'), age_months >= 0, ON DELETE CASCADE
adoption_requests request_id pet_id, adopter_id status IN ('Pending','Approved','Rejected','Completed'), ON DELETE CASCADE
Database Normalization

Normalization (1NF → 3NF / BCNF)

1NF & 2NF Compliance

Every attribute is atomic. Single-column primary keys guarantee no partial functional dependencies.

3NF & BCNF Derivation

If species were kept in PETS, a transitive dependency would exist:

pet_id → species_name (via species_id → species_name)

By extracting SPECIES into its own relation, all transitive dependencies are eliminated. For every non-trivial FD X → Y, X is a superkey, achieving Boyce-Codd Normal Form (BCNF).

Advanced SQL

Relational Views & Analytics

A relational view decouples the client from multi-table join complexity:

CREATE OR REPLACE VIEW available_pets AS
SELECT 
    p.pet_id,
    p.name,
    s.species_name,
    p.breed,
    p.age_months,
    p.status,
    u.full_name AS owner_name,
    u.email AS owner_email
FROM pets p
JOIN species s ON p.species_id = s.species_id
JOIN users u ON p.owner_id = u.user_id;
